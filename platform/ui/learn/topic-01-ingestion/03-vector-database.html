03 · Vector search

Find neighbors in meaning-space

Vector search ranks items by how close their embeddings sit, not by whether the same tokens appear. That is why it shows up in AI-native retrieval: logs, runbooks, images, and audio are unstructured, and equality indexes were never designed for them.

Mechanics

What / why / how

What

Store embeddings with their objects. Search = embed the query, return top-k under cosine or Euclidean distance. “Semantic search” is this ranking applied to language.

Why

A scratch loop over every vector does not survive millions of chunks. ANN (graphs like HNSW, trees, clusters, hashes) buys sub-linear time. You tune recall vs latency vs ingest cost.

How

HNSW: coarse hops on the upper layer, precise walk on the bottom. Hybrid search mixes this with keyword (BM25) so rare tokens — service names, error codes — still win. Libraries (FAISS) hold vectors; a vector database also persists, updates, and filters.

In production

Same geometry, many payloads

Beyond text

Images, audio, video, and mixed queries share one space if the encoder does. English can retrieve a French caption. A photo can retrieve a runbook screenshot.

What it powers

Site search, recommendations, and RAG (neighbors in, LLM out). Speed at tens of millions of passages is the reason this lives in a database, not a dict.

What to pick

Chroma — local first. Pinecone — managed cloud. Weaviate — schema + filters. FAISS/Annoy if you only need an in-memory index.

Checkout is the query vector

Design 1 keeps Chroma on disk (HNSW under the hood). Design 2 is Weaviate. Design 3 is OpenSearch k-NN. We do not brute-force MiniLM vectors in Python at alert time.

Capstone ranking (sketch)

Query: “timeout waiting for redis pool.” Neighbors we want: checkout-redis-pool (high cosine). Neighbors we do not: payment CPU. Keyword-only would miss if the runbook never said “timeout.” Hybrid would still catch the token Redis if the embedding were weak. Tickets stay in PostgreSQL.
