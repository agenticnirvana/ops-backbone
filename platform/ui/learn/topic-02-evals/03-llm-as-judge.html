LLM-as-judge
03 · Judge

A model that grades a model

LLM-as-judge is a second call with a rubric: given the alert, the recommendation, expected vs actual runbook, return {score: 0–1, reason}. It scores qualities exact match cannot — specificity, grounded wording, whether the advice is actually usable.

correctness is ID equality · the judge is prose quality

Intuition

Two roles, two prompts

rubric in the system prompt
JSON only

do not let the judge
invent a runbook_id
— that is correctness’s job
Mechanics

What / why / how

What

A grader LLM. Same stack as the agent in CI (MOCK_LLM returns a stub 0.9). In the live console it can be the real model.

Why

String equality on runbook_id cannot tell “increase REDIS_MAX_CONNECTIONS to 150” from “restart everything.” Operators need that distinction.

How

evals/llm_judge.py → judge_recommendation. Score is recorded per case and published to Langfuse / Phoenix / MLflow. It is not the merge boolean.

In production

Use it. Do not worship it.

Pairwise / rubric

Support orgs grade “was this answer grounded in the retrieved doc?” at scale. Humans spot-check the judge.

Known failure modes

Length bias, self-preference, position bias. A judge that wrote the agent prompt will like its own style.

Split of labor

Exact metrics own the gate. The judge owns a Langfuse score you can trend. Mixing them hides regressions.

This course

SRE judge, JSON back

System: score groundedness, specificity, alignment with the expected runbook. User payload: alert, recommendation preview, expected/actual IDs, keywords. Output clamped to [0, 1].

Capstone

Checkout rec that cites Helm REDIS_MAX_CONNECTIONS scores high even if wording differs from the runbook. A rec that says “restart Postgres” with the right ID still looks bad to the judge — and should.
